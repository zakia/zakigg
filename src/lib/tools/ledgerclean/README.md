# LedgerClean

Local budgeting workspace at `/tools/ledgerclean`. Starts with default categories and zero merchant rules. CSV imports, financial totals, categories, rules, and AI inference stay in the browser.

## Product flow

Recognized CSVs import immediately, group identical and stable merchant descriptions, and open the **Merchants** review tab when unmatched spending remains. Imports have an Undo action. The unified **Overview** combines the monthly spending chart, KPI strip, and searchable ledger table with a month / all-months scope toggle, category/tag filters, manual categorization, and transfer/exclusion options directly in the category picker. Changing a transaction's category automatically learns/updates its merchant rule with a one-click toast to keep the change on **Only this transaction** or **Undo**. A quieter import exception screen asks only for unresolved columns, amount signs, numeric date order, or account identity. Confirmed import profiles are remembered per header layout; filenames and row ordering do not determine the profile. Invalid rows are reported in the import notification; files with no valid records display validation errors.

The eight spending roots are **Business, Household, Dining, Health, Entertainment, Transport, Travel, and Shopping and Personal**. Household includes Housing, Groceries, Bills and Utilities, Home Supplies, and Family and Pets. Dining includes Cafés, Restaurants, and Takeaway; Health includes Medical, Dental, Pharmacy, and Fitness. Savings remains a transfer outside spending. Users can rename, recolor, add, and reparent categories in Settings. Saved IDs, rules, and manual assignments survive adoption of the new default hierarchy.

Purpose tags (Needs, Wants, Mixed; otherwise Unreviewed) are independent of spending categories. Context and pattern tags include Work, Social, Recurring, Subscription, and editable custom contexts. Merchant rules assign defaults; individual transaction overrides can add or remove them. Filtering by a tag updates monthly spending and the transaction table while each amount contributes to exactly one category rollup. A café used for work can be Dining / Cafés plus Work, without becoming a second Business expense.

Recurring detection requires at least three similar charges in the same merchant, account, and currency with a consistent weekly, fortnightly, monthly, quarterly, or yearly cadence. Calendar month ends and small date/amount variations are tolerated. Only charges in the detected series receive the inferred Recurring tag; refunds, transfers, dense daily habits, and different one-off amounts are excluded. Users can remove the inferred tag on a transaction. Sparse history and irregular bills may require manual tagging.

Every valid CSV row counts immediately, regardless of bank status. Purchases count as expenses, refunds offset spending, card repayments and explicit transfers stay out of both expense and income totals. Unclassified money in defaults to income after sign normalization; money out defaults to Uncategorized. Explicit credit-card refunds remain spending offsets. Generic bill payments and pre-authorized debits remain spending until the user marks them as transfers or excludes them. These flags persist and are protected during categorization.

Explicit issuer repayment descriptions (such as “PAYMENT RECEIVED - THANK YOU”) are classified as transfers independently of spending rules, including statements without an account-type column. Repayments are financial activity, independent of merchant-category rules. All previously shipped starter rules are removed on workspace load; approved and imported rules remain intact. Clearing categories and rules therefore preserves repayment treatment. Reloading existing workspaces rederives these rows without changing transaction identities or amounts. Named credit-card payments are also transfers; ordinary chequing receipts and ambiguous bill payments retain their existing treatment.

The **Merchants** view is one merchant workspace: saved rules and unmatched merchants with current transactions share the same searchable table with segmented filter pills (`All merchants`, `Uncategorized`, `Unused rules`). Each group shows net spending by currency (refunds offset, transfers/income/exclusions omitted), using the same matching rows shown in its preview. When local AI is loaded, unmatched merchant groups are automatically pre-filled with AI suggestions, with a one-click **Accept all suggestions** action or per-row **Accept** buttons. Selecting groups explicitly enables reconsideration of already categorized spending too. Income, declared transfers and excluded rows remain outside expense classification. Select merchants and combine them using a substring, prefix, exact description or case-insensitive RE2 regex. The editor previews every match before saving one rule, replacing only selected rules. It prevents incomplete coverage, incompatible financial scopes and overlaps with unselected saved groups. Grouping can be saved as Uncategorized first, then classified once by local AI or assigned manually. AI approval updates the same predicate. Reconsideration shows the saved category beside the proposal and remains unchecked until explicitly reviewed. Approval validates a snapshot of the old rule, preserves its pattern/scopes, and replaces only that rule. The selected rule is excluded from its own model context. Manual transaction exceptions remain unchanged, including when their group is reconsidered. Manual transaction exceptions stay intact; descriptions and dedupe fingerprints never change.

## Ownership

- `processing.ts`: pure PapaParse parsing, integer-cent normalization, rules, filtering, totals, and CSV export. Dates use the shared Temporal-backed `#lib/utils/date.ts`.
- `import-inference.ts`: automatic import proposals and focused ambiguity detection. Explicit purchase activity determines statement signs; otherwise net cash/debit/credit columns and known deposit/repayment conventions provide evidence. For generic amount columns, the most frequent nonzero sign is spending; ties use negative. This counts transactions rather than total value and does not depend on category rules. Explicit bank cash/debit/credit meanings and remembered choices take precedence. Only contradictory typed purchase signs and ambiguous numeric dates ask for confirmation. Confirmed profiles retain columns, account, sign convention, date order, and currency.
- `identity.ts`: account/date/original description/signed amount/currency fingerprints and browser SHA-256 IDs. Overlapping imports preserve the largest observed occurrence count, so identical purchases within a file remain distinct. Existing IDs and edits survive overlaps.
- `categories.ts`: only the spending hierarchy and Savings presets, with stable IDs, names, colors, financial types, classification descriptions and examples. This is the single place to change product defaults and their AI meaning.
- `category-model.ts`: category types, internal bookkeeping states, dictionary construction, validation and reusable category operations. No legacy category mappings.
- `workspace-storage.ts`: strict, versioned local storage at `ledgerclean:workspace:v1`. Schema version 4 stores tags, raw transactions plus explicit overrides, category/rule dictionaries, import metadata/profiles, and `{ enabled }` for local AI. Old provider settings and status fields are discarded on load. Version 1/2/3 workspaces migrate. Automatic categories are derived from rules rather than cached in storage. Corrupt data is preserved and persistence is blocked until explicitly replaced.
- `merchant-workspace.ts` / `MerchantGroupEditor.svelte`: saved-rule grouping, explicit merchant merges and match previews. `rule-pattern.ts` uses RE2JS for linear-time, case-insensitive regex validation and matching; regex source and escapes remain intact. Lookaround and backreferences are unsupported.
- `merchants.ts` / `merchant-rules.ts`: detect stable merchant prefixes before varying references or branch numbers, using at least two distinct observed references. Generic payment/processor labels and conflicting bank labels stay exact. No brand-specific aliases are required: PRESTO FARE and AMZN MKTP CA group independently of their changing codes. Merchant rules match a leading phrase at a word boundary, keeping unrelated prefixes separate. Compatible AI exact rules consolidate on workspace load; manual rules, conflicting categories, and historical exclusion scopes are preserved. Original descriptions, transaction IDs, and signed amounts never change.
- `learning.ts`: shared atomic rule approval. Suggestions become merchant-prefix rules when repeated references provide evidence, otherwise exact-description rules, with account-type and money-direction scopes where needed. Approval saves rules and re-runs the same deterministic matcher over all matching transactions. Conflicting suggestions or existing rule conflicts block approval; there is no new AI assignment-only or future-only path. Explicit manual overrides stay intact. Legacy AI exceptions/scoped exclusions are retained when unrelated rules change. Editing/deleting a learned rule rederives its automatic categories.
- `tags.ts` / `TagPicker.svelte`: tag dictionaries, rule inheritance, explicit transaction overrides, and purpose/context filters.
- `recurring.ts`: Temporal-based payment series detection; inferred tags are derived rather than stored as facts.
- `hierarchical-classification.ts`: eight expense root choices plus Uncategorized first, then only children of a confident selected root. Weak child suggestions retain the parent. Scores combine conservatively across stages; branch-invalid or incomplete mappings apply nothing.
- `ai.ts`: typed classification inputs, compact mappings resolved locally to stable category IDs, validation, and context-aware grouping of repeated merchant descriptions. Stable merchant groups are classified once, with the prefix sent instead of reference codes; conflicting bank/account/category contexts remain separate. Up to 16 groups are classified per batch. Default runs preserve existing rule matches and explicit user decisions before inference; explicit reconsideration runs classify selected spending without committing assignments or rules. Saved rule predicates, category definitions, and bounded approved examples provide the classification context for unmatched expenses. Rule-derived categories contribute through the actual rule dictionary. Example selection considers the whole batch; selected rows are excluded from their own examples. Known income and explicit transfers are deterministic; ordinary spending cannot be assigned to Income or Transfers. Current automatic category differences do not split identical merchants. The worker returns scores and category gaps with every suggestion; malformed confidence is rejected. Failed/incomplete/stale proposals apply nothing.
- `local-ai.svelte.ts` / `ai.worker.ts` / `setfit.ts`: lazy Transformers.js worker running a quantized, transaction-trained SetFit encoder with a supervised logistic head for the eight default spending roots. Category IDs survive renames; missing/custom roots require manual rules. Subcategories and purpose/context tags remain editable, but this classifier only suggests roots. Saved rules apply before inference; the worker does not interpret prompts or retrain on private imports. Scores come from the learned head, not similarity against category descriptions. Below 0.45, a gap below 0.10, or a missing target category yields Uncategorized. Scores from 0.45 to below 0.70 can show a candidate, but it remains unchecked until explicitly reviewed. High requires 0.80 and gap 0.20; these are review thresholds, not calibrated correctness probabilities. Old saved similarity scores retain their original method and meaning. Exported weights are about 23 MB; complete first-use download is approximately 50 MB including WASM. Only versioned same-origin model assets and pinned runtime files are allowlisted, with a 390 MB asset cap and 10 MB reserved for JavaScript. No requests are allowed after loading. Cache identity includes the encoder fingerprint; Settings removes current and obsolete model caches.
- `scripts/ledgerclean-model/`: one offline development training/export script, curated public merchant/type examples, pinned dependencies, and an explicit smoke evaluation report. Browser inference uses ONNX + a JSON linear head; no Python or pickle ships to users. No user CSVs are training data.
- `LocalAiButton.svelte`: shared first-download confirmation, loading progress, retry/cancel, and local inference entry point. No API keys, provider URLs, model selectors, or cloud fallback.
- `AiCategorizer.svelte` / `RuleTransactions.svelte`: unified **Merchants** workspace with segmented filters, automatic AI suggestion prefill, one-click `Accept all suggestions`, inline rule editing, and expandable matches.
- `MonthlySpendingChart.svelte`: unified Overview header combining the month stepper, `All months` scope toggle, year/currency selectors, 4 KPI cards (`Net spending` with MoM delta, `Income`, `Remaining`, and interactive `Needs review` filter), stacked bar chart, and category breakdown.
- `CategoryPicker.svelte`: hierarchical category combobox that also folds `Transfer` and `Exclude from budget` treatment into a single per-row control.
- `index.svelte`: workspace ownership, persistent header import/export actions, 3-tab navigation (`Overview`, `Merchants`, `Settings`), unified Overview + Ledger table, automatic merchant rule learning with `Only this transaction` / `Undo` toast, and structured 2-column `Settings` grid. `ImportQuestions.svelte` owns exception prompts; `CategoryEditor.svelte` and `TagEditor.svelte` own category and tag editing.

## Privacy and local AI

Site analytics are disabled for this route; entering it starts a fresh document. The app bundles its runtime code locally. Enabling AI fetches versioned model/config/tokenizer assets from this app and a pinned WASM runtime from jsDelivr. Requests for these static assets reveal normal connection metadata to their hosts, but transaction prompts never become network requests. There is no hosted inference adapter or automatic remote fallback. AI score shows the classifier head score from 0 to 1, with the gap to the runner-up in the tooltip; historical similarity scores are explicitly identified. It is not measured accuracy or a calibrated probability. Manual assignments and saved rules lacking a model score have no badge; no score is fabricated. Weak suggestions remain unchecked until explicitly reviewed; choosing a category applies it to the entire merchant group. Rules retain the original AI scores, while manually corrected rules do not. Proposed and saved rules expand to show all predicate matches, including protected manual assignments. Classification inputs contain descriptions, relevant bank/account/activity hints, direction, and optional user guidance; account identifiers, source filenames, dates, and amounts are omitted. Prompts and responses are not persisted. Model files use browser cache storage; categories, rules, transactions, and profiles use local storage.

After model loading, categorization can run without networking. Full offline page reload additionally requires caching/serving the application shell; this is not currently a PWA. AI is optional: imports, rules, charts, and manual editing remain usable without a downloaded model. Desktop support is the current target.

## Small-model evaluation

The SetFit evaluation in `scripts/ledgerclean-model/evaluation.json` is a developer smoke fixture, not independently measured real-world accuracy. It includes known brand variants across train and test. This prototype still needs broader, independently labeled merchant evaluation; low scores abstain and every suggested rule requires user approval.

## Deterministic classification contract

Import facts → apply saved rules → suggest exact rules for unmatched expenses → review category/predicate/affected rows → validate and save rules → re-run the same matcher. Category IDs remain stable references. AI never commits a category outside this path, never silently replaces an existing rule, and never creates executable patterns. Fresh workspaces have no starter merchant mappings; existing workspaces discard only rules marked as shipped presets. Selected saved rules can be reconsidered and replaced after explicit review, including same-category score refreshes, with stale rule or transaction snapshots rejected. Users can edit matching patterns directly on merchant groups; substring and regex merges become the same persisted rules used on every import. User overrides and structural transfer handling take precedence. New bank spending rules match money out; credit-card rules include refunds but stay scoped to credit accounts. Category/rule edits and subsequent imports recompute categories without inference. The SetFit classifier is an initial supervised prototype; unseen merchants still require representative evaluation and manual review.
